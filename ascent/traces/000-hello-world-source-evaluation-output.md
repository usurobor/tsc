# Trace 000 — Hello World: source, evaluation, output

**Status:** Bootstrap hand trace
**Purpose:** Exercise the smallest successful Articulation Ascent path — one
frame, one closure, one derived polarity, one inhabited center, one candidate
whole, and an executable oracle. This is the kernel's unit test, not a
showcase; it proves the plumbing before the system tackles Turing.

## Input viewpoint

The Hello World program is its source code:

    print("Hello, world!")

This is not a sophisticated position. It is a locally valid statement carrying
one explicit, exhaustive closure — exactly what a bootstrap needs.

## CompilePOV

**Q — governing question**

    What constitutes this program?

**Γ — locally warranted commitments**

- the source text is a real and necessary articulation of the program;
- its syntax constrains what may occur when it is executed;
- changing the source may change the behavior.

**Ξ — closure assumption**

- the source text exhausts what the program is.

**Σ — available distinctions and operators**

- source text;
- language;
- runtime;
- evaluation;
- execution state;
- observable output.

**R — permitted in-frame moves**

- inspect and transform source syntax;
- compare source files;
- reason statically about the text.

### Compilation result

    FRAME_COMPILED

Frame-fiber size:

    1

The viewpoint is unambiguous: it compiles to exactly one frame. The kernel
does not manufacture alternative readings where the source does not warrant
them. (Contrast Trace 001, whose one sentence compiles to a fiber of three.)

## Support deficit

### Demanded continuation

    Explain why this source produces the observed stdout and exit status.

The source-only frame cannot produce an execution result without a language
semantics, a runtime, and an evaluation relation. The closure that made the
frame self-sufficient is exactly what blocks the demanded continuation.

## Closure core ξ*

    static description exhausts the program

Kind:

    description / execution
    static / dynamic

## Polar closure

Invert the exhaustive closure:

> The program is also articulated by what occurs when the source is evaluated
> in a declared runtime.

Generated polar form:

    source ≡ output

Canonical IR (per D-001):

    Frame(source, Whole, output)

Status:

    POLAR_CLOSURE_FOUND

`source ≡ output` is **not** an equality and not a claim that output is "the
opposite" of code. It is an open program: *find the cohering center through
which source and output belong to one computation.* The right pole was
generated by inverting the closure — it was not handed to the kernel with the
viewpoint.

## Overlap

### Preserved from Γ

- source code remains a genuine articulation;
- syntax continues to constrain execution;
- the source is not dismissed as unreal or merely incidental.

### Held from the polar frame

- observable behavior is also constitutive of what this program does;
- source alone does not determine behavior without semantics and environment.

## Candidate center

    evaluation under the declared language/runtime semantics

Inhabiting the open center completes the frame:

    source evaluation output

The evaluation relation is the cohering role: the process through which the
static source (coherer) and the observable output (cohered) are one
computation.

## Candidate whole

One program execution:

    source
    + declared evaluator/runtime
    + environment
    + resulting observable output

Ascent-fiber size:

    1

Exactly one whole is warranted. No underdetermination to retain.

## Executable oracle

Run the pinned source under the pinned runtime.

Fixture:

    print("Hello, world!")        # pinned Python 3 runtime

Expected:

    stdout      = "Hello, world!\n"
    exit_status = 0

The cohered pole is checked *directly*: the output is the observable
projection of the execution, and here that projection is total and trivial —
which is the whole point of a bootstrap oracle.

## Result

    ASCENT_COMMITTED

Warrant class:

    EXECUTABLE_CONSTRUCTION

The whole is constructed and then verified by executing it. This is distinct
from an informal warrant (Trace 001), a formal proof (Trace 002), and an
oracle that checks a *predicted consequence* (Trace 003): here the oracle
checks the constructed right pole itself.

## Support expansion

The completed frame `source evaluation output` can now draw distinctions the
source-only frame could not:

- the same source may produce different output under a different environment
  or semantics — so the evaluator/runtime is part of the warranted account,
  not incidental;
- different source programs may produce the same output — so source
  equivalence and behavioral equivalence are not the same relation;
- the full execution behavior (the trace) is the general cohered pole; the
  output is its observable projection, which is what makes this instance
  mechanically checkable.

## Migration audit

Old statement:

    The program is its source code.

Migrated statement:

> Source code is one articulation of a program execution. Observable output is
> another. Evaluation under declared semantics is the cohering relation
> through which the two belong to one computation.

Status:

    MIGRATED

The source claim is not discarded — it loses only its *exhaustiveness*. It
remains locally true (the source is a real, necessary articulation) inside a
larger warranted account.

## Decorative failure (what would not count)

The following is insufficient:

> Code and output are both aspects of the program.

It names no center, no execution semantics, no oracle, and no discriminating
consequence. It would return:

    DECORATIVE_LIFT

## Honest read

The trace is intentionally trivial. It succeeds only if the kernel reconstructs
the operational-semantics structure — coherer / cohering / cohered as source /
evaluation / output — without ambiguity, and the result can be checked by
running the program. Hello World proves the method can take one step. The
later traces determine whether it can walk.
